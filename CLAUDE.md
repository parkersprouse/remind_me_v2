# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tauri v2 (Vue 3 + TypeScript + Pinia + Vite) rewrite of the Flutter app at `~/Code/GSS/remind-me`, migrated 1-1 in functionality and design. **The Flutter source is the behavior/design reference — preserve parity unless told otherwise.**

## Commands

```sh
pnpm install
pnpm build            # vue-tsc typecheck + vite bundle (frontend only)
pnpm lint             # eslint
```

There are no tests configured; `pnpm build` (typecheck) plus `pnpm lint` are the main correctness gates. There is no desktop or browser dev/build target — see Architecture below.

### Android

```sh
pnpm tauri android build --debug --target aarch64
# APK: src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk
adb install -r <apk>
adb shell am start -n software.greysky.remindme/.MainActivity
```

- **Signed release builds:** `pnpm tauri android build --apk` produces `.../apk/universal/release/app-universal-release.apk`. Signing is wired into `gen/android/app/build.gradle.kts` (release `signingConfig`), which reads `gen/android/keystore.properties` (gitignored; template at `keystore.properties.example`). The block is guarded on that file's existence — absent it, the release build stays *unsigned* rather than breaking `debug`. Release is minified (R8); the reflective Tauri plugin surface + `@JavascriptInterface` bridge survive via the AAR's consumer ProGuard rules (confirmed by exercising notifications on the signed release APK). Those generic rules do **not** cover the notification plugin's plain Jackson model types (`NotificationInterval`, `DateMatch`, …) — repeat schedules broke on release builds only until the vendored plugin's `consumer-rules.pro` added `-keep class app.tauri.notification.** { *; }`; don't remove it, and re-verify *repeating* reminders (not just one-shots) when touching ProGuard config. Full process in [RELEASE.md](RELEASE.md).
- Wait ~8s after launch before sending adb input events, or an ANR dialog kills the app.
- Stale dev-cache gotcha: if the installed APK shows "Failed to request http://localhost:1420/", a prior `tauri android dev` left dev-mode build-script output in the cargo cache. Fix: `cd src-tauri && cargo clean -p remind_me && touch build.rs`, then rebuild.
- Inspect live JS state via WebView CDP: `adb forward tcp:9223 localabstract:webview_devtools_remote_$(adb shell pidof software.greysky.remindme)` then `Runtime.evaluate` over WebSocket. Re-forward after every app restart. Prefer CDP evals over screenshots for asserting app state.
- `pnpm tauri android build` picks Android Studio's bundled JBR (Java 25) by default when `JAVA_HOME` is unset, which fails Gradle's `:buildSrc` configuration with a cryptic `> 25.0.2` error. Fix: `export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` before building.
- Testing a deep link via `adb shell am start -d "remindme://...&..."` silently truncates at the `&`: adb joins argv into one string and hands it to the *device's* shell, which treats an unescaped `&` as a background operator. Wrap the whole `-d` value in single quotes inside the outer double-quoted command instead, e.g. `adb shell "am start -a android.intent.action.VIEW -d 'remindme://create?details=x&at=y'"`.
- `withGlobalTauri` is enabled in `tauri.conf.json`, so CDP evals can drive the backend directly via `window.__TAURI__.core.invoke(...)` (e.g. `plugin:notification|notify`, `plugin:notification|cancel`).
- The app DB is WAL-mode SQLite at `/data/data/software.greysky.remindme/reminders.db`; to inspect it, `run-as` cat **all three** files (`.db`, `.db-wal`, `.db-shm`) to the host, then open with local `sqlite3` — pulling only the `.db` shows stale pre-checkpoint data.

## Architecture

**Thin Rust backend, logic lives in the frontend.** `src-tauri/src/lib.rs` only registers plugins and defines the SQLite migration (the `reminders` table schema — matches the Flutter sqflite schema exactly). It exposes no custom commands. Everything else is TypeScript.

**No vue-router.** Navigation is a tiny Pinia store (`src/stores/router.ts`) that switches between three pages (`landing` / `home` / `settings`) plus a home tab index — an IndexedStack-style switcher mirroring the Flutter RouterModel. Its `back()` action encodes the Android back-button policy.

**Android-only — no platform abstraction.** This app targets Android exclusively; there are no desktop or browser-dev code paths (they were removed — the git history has the pre-collapse version if ever needed). Reminders are scheduled through the Android OS notification system (`Schedule.at` in `src/lib/notifications.ts`) with snooze action buttons, so they fire whether or not the app is running. A high-importance channel (`reminders_high`) makes them pop heads-up; channel importance is frozen by the OS at creation, so changing it requires renaming the channel id. There is no `isTauri`/`isMobile` guarding — code assumes the Android/Tauri webview is always present. Verification is therefore `pnpm build` (typecheck) **plus** an Android build; there is no `pnpm dev` browser loop anymore.

**Persistence:** `reminders.db` via tauri-plugin-sql (frontend queries in `src/lib/db.ts`; table created by the Rust migration, not by the frontend) and `settings.json` via tauri-plugin-store (`src/stores/settings.ts`).

**Startup order matters** (`src/main.ts`): mount the app first, then register the Android back handler (needs active Pinia), then run async init (settings → notification channel/actions → expired cleanup).

**Theming is generated at runtime, not authored.** The Material 3 palette comes from one user-chosen seed color (`accentColor` in the settings store) expanded by `@material/material-color-utilities` in `src/lib/theme.ts`, which writes ~30 tokens as **inline custom properties on `<html>`**. The seed is chosen in `AccentColorPicker.vue` (preset swatches) and `ColorPickerDialog.vue` (wheel / RGB / hex), the latter backed by the pure HSV conversions in `src/lib/color.ts`. A watcher in `App.vue` re-runs it whenever the resolved theme (`light`/`dark`, `'system'` resolved via `matchMedia`) or the seed changes, and also sets `data-theme`. `src/assets/styles/theme.css` still holds the static blue scheme, but at runtime it is only the **pre-hydration fallback** — the inline vars always win, so editing hex values there changes nothing once the app has painted. Add new tokens to the `TOKENS` map in `theme.ts`, not just the CSS.

## Gotchas

- **Capabilities:** any new plugin API call needs a matching permission in `src-tauri/capabilities/default.json`. A missing permission fails silently — the invoke promise rejects but the notification shim is fire-and-forget and native logs show nothing. Android OS permissions (e.g. `SCHEDULE_EXACT_ALARM`) additionally go in `src-tauri/gen/android/app/src/main/AndroidManifest.xml`.
- **`src-tauri/gen/android/` contains hand edits.** `MainActivity.kt` intercepts back presses via `OnBackPressedCallback` and evaluates `window.androidBackHandler()` in the webview (bridge in `src/lib/androidBack.ts`), and delivers notification action taps to `window.androidNotificationAction(id, actionId)` and external create requests to `window.androidCreateRequest(request)` (see below) with retry polling — the plugin's own `actionPerformed` event is unusable (dropped on cold start, payload lacks the notification id). Its `onResume()` calls `window.androidResume()` (registered in `App.vue`) to re-run the notification-permission gate on foreground — the DOM `window` `focus` event does not fire on Android Activity resume, so without this bridge the landing page would never advance after the user enables notifications in system settings. It also exposes a JS→native bridge as `window.AndroidNative` (`@JavascriptInterface`, typed in `src/lib/androidNative.ts`) whose `openNotificationSettings()` launches the Android app-notification-settings Intent — called by `LandingView.vue` on the permission-denied path (gated on API 26+, falling back to the app detail page on 24–25) — and whose `exportBackup(json, fileName)` / `importBackup()` launch SAF document pickers for the Settings → Backup feature, delivering their outcome back through `window.androidBackupResult` (consumed by `src/lib/backup.ts`), and whose `takePendingOps()` / `setNotificationActionGroup(id)` serve the receiver journal and the headless-create path (both below). The tree also holds `SnoozeActionReceiver.kt`, `CreateReminderReceiver.kt`, `QuickCreateWidgetProvider.kt` (with `res/layout/widget_quick_create.xml`, `res/xml/quick_create_widget_info.xml` and the `res/drawable/widget_*` + `ic_widget_plus` drawables), `ReminderListWidgetProvider.kt` / `ReminderListWidgetService.kt` / `WidgetSnapshot.kt` (with `res/layout/widget_reminder_list.xml`, `res/layout/widget_reminder_row.xml` and `res/xml/reminder_list_widget_info.xml`), `PendingOpsJournal.kt` and `NotificationActionGroup.kt`, and the manifest has manual permission additions plus all four receivers' and the collection service's registrations. Don't regenerate or blindly overwrite this tree.
- **External reminder creation (deep link + share) reuses the notification-action replay guard.** `remindme://create?details=...&at=...` (`VIEW`/`BROWSABLE`) and share-sheet `ACTION_SEND text/plain` are both parsed by `extractCreateRequest()` in `MainActivity.kt` into a `CreateRequest`, delivered to `window.androidCreateRequest(request)` with the same cold-start retry as a notification action, and covered by the same `HANDLED_ACTION_KEY`/`fingerprint()`/`FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY` replay guard — `fingerprint()` falls back from a notification action's `id|actionId` to the request's `replayKey` (the full URI for a deep link, so a caller-supplied `key` query param rides along for free; the shared text itself for a share) so relaunching the task from Recents can't silently create a duplicate reminder. `src/lib/createRequest.ts` decides what happens with a parsed request: a share always prefills the New Reminder form (`ReminderForm.prefill()`, applied by `NewReminderTab.vue` on mount and via watch so a request arriving before that tab has ever rendered isn't lost); a deep link with both details and a still-future `at`, and notification permission already granted, schedules the reminder outright via `notification_manager.schedule()` and toasts — anything short of that (missing time, ungranted permission, or a schedule failure) falls back to prefill instead of silently dropping the request.

  **A *details-less* deep link is a navigate request, not a create one** (phase 2): bare `remindme://create` just routes to Home / New Reminder, deliberately *without* prefilling or resetting the form — `ReminderForm.prefill()` assigns `form.details` unconditionally, so routing an empty request through it would wipe a half-typed reminder, which the launcher icon doesn't do either. That is exactly what the launcher shortcut in `res/xml/shortcuts.xml` fires (registered by the `android.app.shortcuts` meta-data on the MAIN/LAUNCHER activity; `<intent android:data=...>` is undocumented but honoured — verify with `dumpsys shortcut`). Because such a request creates nothing, it is **exempt from the replay guard** — dedup is meaningless for it. `CreateRequest.isCreate` in `MainActivity.kt` gates both `fingerprint()` and the `handledActionFingerprint` write, and mirrors `normalizeDetails()`'s blank test — keep the two in sync.

  **Two replay-guard fixes came out of verifying that** (both shipped duplicate reminders since phase 1, both reproduced on the signed release APK). `onCreate` must **restore** `handledActionFingerprint` from `savedInstanceState`, not merely compare against it: a suppressed pass records nothing, so the next `onSaveInstanceState` wrote null and the recreation after that replayed the create — the guard survived exactly one recreation. And `onNewIntent` must call **`setIntent(intent)`**: neither `Activity` nor Tauri's `TauriActivity`/`WryActivity` does, so `getIntent()` otherwise still returns the *launch* intent after a recreation, and a second deep-link create in one session left the first looking unhandled. To reproduce this class of bug, change the system font scale (`adb shell settings put system font_scale 1.3`) — `fontScale` is deliberately absent from the activity's `configChanges`, so each change recreates the activity in-process with its saved state, which no other easily-triggered gesture does. The shortcut's `shortcutShortLabel` is what launchers usually render (the long label is promoted only when it fits the popup), and its icon is a dedicated disc-plus-glyph drawable rather than `ic_stat_logo`, which is alpha-only white and invisible on a light launcher. Details are capped to `DetailsInput.vue`'s 240-char limit before they reach the form or the DB, since a request can come from any installed app or a bare URL. Emulator-verified: full auto-create, missing-time prefill, and share prefill, via WebView CDP plus direct `reminders.db` queries.

- **Preset snooze buttons never open the app; "Custom…" does.** A notification action's `PendingIntent` kind is fixed at creation, so "don't launch the app" is not a flag — it's `getBroadcast` instead of `getActivity`. The vendored plugin now honors the `foreground` field the JS `Action` interface always exposed (upstream parsed it on iOS only): `foreground: false` routes the tap to the package-scoped `BACKGROUND_ACTION_BROADCAST` instead of `MainActivity`. `registerSnoozeActions()` marks the presets `false` and `Custom…` `true` — the custom flow needs the in-app dialog, so it *must* stay on the Activity path. That PendingIntent is deliberately `FLAG_IMMUTABLE` (Android 14+ rejects a mutable PendingIntent wrapping an implicit intent; mutability is only needed for `RemoteInput`, which a background action can't use).

  There is no webview in a receiver, so the snooze splits in two. `SnoozeActionReceiver.kt` does only what cannot wait for the app to be reopened — dismiss the notification and arm the snoozed copy — rebuilding it entirely from the serialized notification the intent carries (body, `channelId`, `icon`, `actionTypeId` all ride along, so no reminder constants are duplicated in Kotlin). The `reminders.db` bookkeeping is journaled to SharedPreferences and applied by `drainPendingOps()` in `src/lib/notifications.ts`, which runs at startup (**before** `cleanExpired()`), from `androidResume`, and from a `PENDING_OPS_UPDATED` broadcast — that last one exists because the shade is an overlay, so snoozing while the app is foregrounded produces no resume and the list would otherwise sit stale. Kotlin deliberately never touches the SQLite file: the one-shot-vs-repeat semantics live in TypeScript, and the receiver's `newId` is shared by the armed alarm and the journal row so a re-drain is idempotent. Emulator-verified on debug **and** minified release, with the process killed, for one-shot and repeating sources.
- **Headless reminder creation is a broadcast, and its journal is shared with the snooze path.** `CreateReminderReceiver.kt` (action `software.greysky.remindme.CREATE_REMINDER`, deliberately `exported="true"` — automation apps can hold no signature or custom permission, so the mitigation is input validation) arms a one-shot via the same vendored `scheduleNotificationInBackground` the snooze uses, then journals the DB row for `drainPendingOps()`. Caller contract in [README.md](README.md#automation); design and verification in [PLAN.md](PLAN.md) phase 3. Things that bite:

  - **`PendingOpsJournal.kt`'s SharedPreferences store is still named `SNOOZE_JOURNAL`** even though everything around it generalized, because prefs survive an app update and a rename would orphan entries written by the shipped build. For the same reason a journal entry with **no `type` field is read as a snooze**. Don't "tidy" either.
  - **A headless create has no source notification to copy**, unlike a snooze, so `CHANNEL_ID` / title / `ic_stat_logo` are duplicated in the receiver (mirror comments both sides). The one value that *isn't* constant — whether snooze buttons exist — is mirrored natively by `registerSnoozeActions()` through `setNotificationActionGroup` into `NotificationActionGroup.kt`. Kotlin cannot read it instead: `NotificationStorage`'s constructor takes an `ObjectMapper`, which the module seam forbids. Absent/empty means "arm without buttons", never "drop the request".
  - **That mirror needs the settings watcher in `init()`**, not just the refresh inside `arm()`: `arm()` re-registers before every in-app notify, but a broadcast reads whatever was registered last, so toggling snooze off otherwise left buttons on headless reminders until the next in-app schedule.
  - **Repeats are rejected, not downgraded** (rules live in `repeat.ts`; porting `nextOccurrence()` to Kotlin isn't worth it), and nothing fails silently — every path logs and sets a distinct `resultCode` when the broadcast is ordered, which `adb shell am broadcast` prints. `result=0` means the receiver never ran: wrong component/action, or the app is force-stopped (Android's stopped-state rule, same caveat as `BOOT_COMPLETED`). Note `am kill`, not `am force-stop`, is what simulates "process died normally" when testing.
  - Numeric extras are read type-tolerantly (`--el` / `--ei` / `--es`): a typed getter silently returns its default for the wrong type, which reads as "absent" and produces a baffling rejection.

- **`activeNotificationIds()` must not use the plugin's `active()` wrapper.** That wrapper types the raw Android payload (`{"values":[{"nameValuePairs":{"id":…}}]}`) as `ActiveNotification[]` — there is no Rust command backing `get_active`, so the invoke is forwarded straight to Kotlin and its `JSArray` return value is serialized by reflection over the org.json internals. `.map()` over that threw into the `catch`, so the "still in the drawer, leave it alone" guard in `cleanExpired()` never fired and every launch deleted the row of a reminder that had fired while the app was closed *and* dismissed its still-visible notification (via `cancelPending`), snooze buttons and all. Fixed by invoking `plugin:notification|get_active` directly and unwrapping `values[].nameValuePairs.id`, the way `permissions.status()` already bypasses its wrapper; ids are coerced with `Number` because a string id would miss every `Set` lookup *without* throwing — the same bug in disguise. Emulator-verified in all three directions: notification present → row survives, notification dismissed → row swept on next launch, preset snooze on a surviving notification → source row replaced by exactly one copy and one armed alarm.

- **The quick-create widget's buttons go through its own provider, not straight to `CreateReminderReceiver`.** `QuickCreateWidgetProvider.kt` (+ `res/layout/widget_quick_create.xml`, `res/xml/quick_create_widget_info.xml`) is phase 4: preset buttons that arm a reminder headlessly and a "+" that fires the details-less deep link. Each preset tap goes to the provider's own `ACTION_QUICK_CREATE` and is forwarded to `CreateReminderReceiver` by explicit component, purely so the widget can repaint a confirmation line — a create broadcast is silent until the reminder fires, and a home-screen button that visibly does nothing reads as broken. Don't "simplify" it by pointing the `PendingIntent` at the receiver, and don't add a UI/toast flag to the receiver instead: its extras are the published automation contract in [README.md](README.md#automation). The confirmation is optimistic (a plain `sendBroadcast` has no result code, and a preset request can't fail validation), past-tense on purpose (`updatePeriodMillis` is 0, so nothing repaints it between taps — a present-tense line would rot), and reverts to the hint on the next `onUpdate`. Things that bite:

  - **`PendingIntent` identity ignores extras** (`Intent.filterEquals`), so all three buttons — across every placed instance — collapse onto one `PendingIntent` unless something else distinguishes them, and `FLAG_UPDATE_CURRENT` then leaves every button doing whatever was registered last. Each carries a `remindme-widget://quick-create/<widgetId>/<minutes>` data URI *and* a derived request code. This one looks fine in a screenshot; check the log for three different durations.
  - **A widget provider must be `exported="true"`** (the launcher is another process), so its click action is externally reachable even though the app's own `PendingIntent`s are explicit. Hence the duration range check in the provider on top of the receiver's own validation — same posture as phase 3. Its custom action deliberately has **no** intent filter, which keeps it off the implicit-broadcast surface.
  - **The widget is `RemoteViews`, so the runtime M3 palette is unreachable.** Colours are static `@color/widget_*` with a `values-night` variant (buttons reuse `@color/ic_launcher_background`, as `ic_shortcut_new_reminder` already does), which means the widget follows the *system* light/dark setting, not the app's own `theme` setting. Same reason the presets are hardcoded rather than read from `quickScheduleOptions`: a widget placed before the app was ever opened must still render usable buttons. Phase 5's snapshot bridge is what changes both.
  - **A force-stopped app's buttons are silently dead**, since a manifest receiver gets no broadcast in Android's stopped state — the same caveat `BOOT_COMPLETED` and the phase-3 broadcast carry, but here it surfaces as a home-screen button that does nothing. A *fresh install* is not the same case: binding the widget takes the app out of that state, so the first tap on a never-launched install does work (verified).
  - **Verification is screenshots** — CDP evals don't reach `RemoteViews`. Placement is manual through the launcher's widget picker (`adb shell cmd appwidget` doesn't exist); `adb shell input draganddrop` works for dropping it on the home screen, and `adb shell dumpsys appwidget` confirms the provider registered and the instance bound. `adb shell cmd uimode night no|yes` flips the `values-night` variant.

- **The reminder-list widget renders a snapshot the frontend pushes; Kotlin never reads `reminders.db`.** Phase 5: `src/lib/widget.ts` builds a denormalized JSON snapshot — already-formatted rows (`formatEpoch` / `describeRepeat`, the same split `ReminderListEntry.vue` makes) plus *both* colour schemes — and hands it to `WidgetSnapshot.kt` through `AndroidNative.setWidgetSnapshot`, which stores it in SharedPreferences and repaints. That keeps the formatting and repeat logic in one language, avoids a second SQLite connection against a WAL database, and — because prefs survive reboot and app update — the widget shows real reminders on a device that hasn't opened the app in weeks. It is pushed from `onRemindersChanged` plus a watcher on `theme`/`accentColor`/`systemPrefersDark`, and once at the end of `main.ts`'s init. Only the frontend ever writes it, so a background snooze or headless create with the app closed leaves it stale until next open — accepted, since a receiver has raw `details`/`fireAt` and cannot produce a formatted row without also reading `settings.json` from Kotlin. A fired one-shot is instead dropped at render time, deliberately diverging from `cleanExpired()`, which keeps such a row while its notification is still in the drawer. Things that bite:

  - **A full `updateAppWidget` from the app is dropped whenever the RemoteViews carry a `setRemoteAdapter`.** The platform logs `Trying to notify widget update deferred` and only the `APPWIDGET_UPDATE` broadcast's own `onUpdate` gets through. The symptom is lopsided and misleading: the *rows* keep refreshing (the host re-queries the `RemoteViewsFactory` directly), so you get a current list in a stale palette — light text on a dark panel. `refresh()` therefore sends `partiallyUpdateAppWidget` with a **chrome-only** RemoteViews, which merges into the stored views and lands; the full `buildViews` (adapter, empty view, click targets) is `onUpdate`'s job alone, and a partial update requires one of those first. Bouncing the call through a broadcast to the provider and `updateAppWidget(ComponentName, …)` both look like fixes and are not.
  - **Snapshot colours are plain ints, so they can't follow the system night setting** the way a `@color` with a `values-night` variant does, and nothing can repaint them — Android delivers no configuration-change broadcast a manifest receiver may subscribe to. `setSnapshotColor()` in `WidgetSnapshot.kt` uses `RemoteViews.setColorInt(viewId, method, notNight, night)`, which ships both values and lets the host pick per its own configuration on every apply. That is API 31+; below it a 'system' theme resolves once at push time, which is what the `systemPrefersDark` watcher mitigates. An explicit light/dark setting needs none of this, and is why the widget follows the *app's* theme rather than the launcher's — unlike the quick-create widget.
  - **The panel is an ImageView, not a background.** Tinting a rounded background is impossible below API 31, so `widget_panel.xml` is a white rounded rect drawn as `src` and recoloured with `ImageView.setColorFilter` (SRC_ATOP, so the rounded alpha survives). Same trick for the row divider — and the divider colour is pushed **opaque** on purpose, since a colour filter composites onto the source and cannot apply alpha. The meta line's 0.66 alpha rides along in `#AARRGGBB` instead, because `setTextColor` blends.
  - **The `RemoteViewsFactory` must read the snapshot in `onDataSetChanged`, not its constructor** — a factory is created once per binding, so a constructor read renders correctly exactly once and never updates. It also serves `getCount`/`getViewAt` from that one copy, since `onDataSetChanged` runs on a binder thread.
  - **`remindme://reminders` is navigate-only, and parsed without reading its query string** on both sides (`MainActivity.kt`, `src/lib/createRequest.ts`). The filter is `BROWSABLE`, so any web page can send one; letting `details`/`at` ride along would turn it into a second create surface outside phase 1's replay guard. `CreateRequest.target` is what distinguishes it from `remindme://create`.
  - **Collection children can't carry their own `PendingIntent`.** Rows use `setPendingIntentTemplate` + an empty `setOnClickFillInIntent`, with the whole intent on the template (which also sidesteps `Intent.fillIn`'s "template data wins" rule). That template must be `FLAG_MUTABLE` — legal because it names its component, unlike the implicit-intent case phase 4's `FLAG_IMMUTABLE` note cites — and it needs its own request code, since a `PendingIntent`'s identity ignores mutability and it would otherwise share one with the header's immutable "open the list" tap.

- **The app bar and toasts are deliberately always-dark.** They use the `--dark-*` tokens in `src/assets/styles/theme.css` (app bar background is a literal `#000000`), carried over from the Flutter app, and are intentionally *not* driven by the seed color. `applyDynamicColor()` must keep leaving them alone. Likewise `--divider` is defined relative to `--outline-variant` and follows it automatically — don't add it to the `TOKENS` map.
- **`navigator.clipboard.writeText()` works — no clipboard plugin needed.** The webview origin is `http://tauri.localhost`, and Chromium treats `*.localhost` as a potentially-trustworthy origin, so `window.isSecureContext` is `true` and the async Clipboard API is present (verified on-device; used by the copy button in `ColorPickerDialog.vue`). Only `writeText` is available: `readText()` returns "Read permission denied", and a CDP `Runtime.evaluate` of `writeText` fails with "Document is not focused" even though a real tap succeeds — so test the copy path with `adb shell input tap`, not a CDP eval.
- **The accent color picker is in-app, not `<input type="color">`.** The platform color dialog cannot be seeded with the current color (it always opens on black) and injects its own suggestion swatches, so `ColorPickerDialog.vue` replaces it. Inside it, `rgb` is canonical and `hsv` is the wheel's own state; each interaction writes one and derives the other. Do **not** collapse them into a two-way watch: re-deriving `hsv` from `rgb` drops the hue of any neutral (chroma 0 has no angle, so dragging brightness to black and back would snap the hue to red), and re-deriving `rgb` from a rounded `hsv` drifts the hex away from the color the dialog opened on. The wheel needs no canvas — a `radial-gradient` white veil over a `conic-gradient` hue ring *is* HSV at `v=1` (at radius `r` the white alpha is `1 − r/R`, giving `hue·s + white·(1−s)`), and a black overlay at `opacity: 1 − v` applies value. It needs `touch-action: none`, or the WebView claims the drag for its own pan gesture.
- **Safe-area insets:** Android WebView never populates `env(safe-area-inset-*)`; the `@saurl/tauri-plugin-safe-area-insets-css-api` side-effect import in `main.ts` keeps `--safe-area-inset-top/bottom` CSS vars in sync. Layout must use those vars, not `env()`.
- **`tauri-plugin-notification` is vendored** at `src-tauri/vendored/tauri-plugin-notification` via `[patch.crates-io]`: upstream 2.3.3 stores action buttons under the wrong SharedPreferences keys, so every action renders with an empty title and reports an empty action id when tapped (fix + explanation in the vendored `NotificationStorage.kt`). The vendored `android/consumer-rules.pro` is also a fix: upstream declares it in `build.gradle.kts` but never shipped the file, so minified release builds stripped the plugin's Jackson-reflected model classes — `Schedule.every` notifications rejected with "No enum constants for class NotificationInterval" and `Schedule.interval` DateMatch fields silently deserialized to null (debug builds unaffected). Before upgrading the plugin, check whether upstream fixed `writeActionGroup`; the plugin's `onAction` event is separately unusable on Android (payload lacks the notification id, cold-start events are dropped) — foreground action taps flow through the `MainActivity.kt` → `window.androidNotificationAction` bridge instead, and background ones through `BACKGROUND_ACTION_BROADCAST` (see above). Two further vendored additions support that: `NotificationAction.foreground` (parsed + persisted in `NotificationStorage`, defaulting to `true` so unmarked actions behave as before) and the Jackson-free entry points `Notification.fromJson` / `scheduleNotificationInBackground` — Jackson is an `implementation` dependency of the plugin module, so **any signature the app calls must not mention an `ObjectMapper`** or it won't compile from `gen/android`. `scheduleNotificationInBackground` also pairs `schedule()` with `appendNotifications()`, which is required for reboot survival: the manager only arms the alarm.
- **Reboot survival is also a vendored fix.** Upstream 2.3.3's boot-restore receiver was a silent no-op (scheduled reminders died with every reboot): `show` never persisted to `NotificationStorage`, the store wrote the never-assigned `sourceJson` (the literal string `"null"`), the broadcast receivers read back with a bare `ObjectMapper()` that cannot parse what Tauri's field-visibility invoke mapper wrote, and repeating (`Every`) entries were evicted from the store after their first fire. All four are fixed in the vendored plugin (comments marked `VENDORED FIX` in `NotificationPlugin.kt`, `NotificationStorage.kt`, `TauriNotificationManager.kt`, `NotificationSchedule.kt`); receivers must use `storageJsonMapper()`, never a bare `ObjectMapper()`. Emulator-verified across `adb reboot`: future reminders re-arm exactly at their original time, and reminders missed while powered off fire ~15s after boot — both without the app being opened. Caveat: a force-stopped app doesn't receive `BOOT_COMPLETED` (Android stopped-state rule); those reminders recover via the `cleanExpired()` launch sweep on next open.
- **Notification permission must be read natively, not via the plugin's `isPermissionGranted()`.** That JS wrapper short-circuits on the webview's cached `window.Notification.permission`, which freezes at `'denied'` once `requestPermission()` is rejected and never re-syncs when the user later enables notifications in system settings (only a process restart re-reads it). So `Permissions.status()` in `src/lib/notifications.ts` invokes `plugin:notification|is_permission_granted` directly (`=== true`; native returns `true`/`false`/`null`). Combined with the `androidResume` bridge above, this is what lets the landing → home gate open on return from settings. Don't "simplify" it back to the wrapper.
- **App icons are Flutter's, adaptive-only.** Launcher = foreground vector `res/drawable/ic_launcher_foreground.xml` + `@color/ic_launcher_background` (`#3F6194`), wired in `res/mipmap-anydpi-v26/ic_launcher.xml`; there are deliberately **no raster launcher fallbacks and no `drawable-v24` foreground** (a `-v24`-qualified drawable would shadow the plain one on the API-26+ devices that use adaptive icons — the classic silent "wrong icon still ships" trap). The notification **small icon** is a separate monochrome glyph at `res/drawable-anydpi/ic_stat_logo.xml`, selected via `icon: 'ic_stat_logo'` in `arm()` (`src/lib/notifications.ts`); Android draws small icons from alpha alone, so without it the plugin falls back to the launcher icon and it renders as a white square. Don't drop the `icon` field or re-add raster/`-v24` launcher variants. The desktop/store/iOS set under `src-tauri/icons/` was regenerated from the same mark via `pnpm tauri icon <1024².png>` (source = the adaptive icon rendered to PNG). **Caveat: `tauri icon` also rewrites `gen/android/.../res/` — it recreates the raster mipmaps and resets `mipmap-anydpi-v26/ic_launcher.xml` + `values/ic_launcher_background.xml` to its own defaults**, clobbering the adaptive-only setup above. After running it, re-apply the three Android edits (foreground → `@drawable/ic_launcher_foreground`, background color → `#3F6194`, delete the recreated `mipmap-*/ic_launcher*.png`).
- **`minSdk = 26`** (`gen/android/app/build.gradle.kts`). Chosen so the icons can be adaptive-only and because notification channels (the `reminders_high` heads-up channel) are an API-26 feature anyway. Note this makes the API 24–25 fallback branch in `LandingView.vue`'s `openNotificationSettings()` (and the "24–25" note above) unreachable dead code.
- **`[profile.dev] strip = "debuginfo"`** in `src-tauri/Cargo.toml` keeps debug APKs ~30MB instead of ~326MB. Don't remove it.
- **Backups are explicit, never automatic.** `android:allowBackup="false"` in the manifest: Android Auto Backup would restore `reminders.db` on reinstall but never re-arm the OS alarms (restore doesn't run the boot receiver), leaving reminders visible but silent. Instead, Settings → Backup exports a versioned JSON file (`src/lib/backup.ts`) via a SAF "create document" picker, and import merges it back by scheduling each entry through `notification_manager.schedule()` — which is what actually arms the alarms. Import skips exact duplicates and already-expired one-shots, mints fresh ids, and preserves chained-repeat anchors. Don't re-enable Auto Backup without also solving the un-armed-restore problem.
- **Font Awesome:** the Flutter app used FA Pro icons; this rewrite uses the free set plus the `BadgedIcon` component as a stand-in. The `@fortawesome` scope must resolve to registry.npmjs.org (Pro registry returns 401 on this machine).
